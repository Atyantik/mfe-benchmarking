A guided version of the technical report

What We Measured, In Plain Words

The same website, built twice — once with React and once with Svelte — then measured under identical conditions. Every number here appears in the technical report too; this version explains what each one means and why it might matter.

What we did, in three sentences

We built the same website twice. Same pages, same content, same layout — one version written with React, the other with Svelte. Everything else was held identical so that any difference is caused by the framework and nothing else.

We then loaded every page 3 times per version, on a deliberately slowed-down machine and connection, and recorded 251 different measurements each time.

Below, each measurement gets a plain description and its own chart. Blue is React, orange is Svelte. Shorter bars are better everywhere except where it says otherwise.

How to read the charts

The bar

The average of all runs. Blue is React, orange is Svelte.

The thin line through it

How much the number moved between runs. A short line means we measured the same thing every time; a long one means the number is unreliable and should not be used to pick a winner.

The dotted red line

The point at which the industry calls a result "good", where such a standard exists. Bars past it are a problem regardless of which version is ahead.

The conditions we measured under

This is the part most easily got wrong, and it changes every number below. The machine running these tests is much faster than the phone a real visitor uses, and everything runs on that one machine with no network in between — so left alone, it would make every version look equally fast and hide every difference.

So we deliberately made things worse, on purpose, in four ways:

Slowed-down processor

We made the browser four times slower than this machine

4× slower

The computer running these tests is far faster than the phone most visitors use. Measuring on it would make every version look equally fast and hide every difference. Four times slower is what Google’s own tooling uses to stand in for a mid-range phone.

Slow connection

We limited the connection to roughly a poor 4G signal

1638 Kbps down · 750 Kbps up · 150 ms delay

This matters more than it sounds. Everything here runs on one machine, where downloads are instant — so a page that downloads twice as much appears to cost nothing extra. With a realistic connection, weight turns back into waiting. Before this was added, two versions differing by 31% in download size reported an identical loading time.

Fewer processor cores

We told the browser it had four cores instead of fourteen

4 cores

Some code checks how many cores are available and does more work when there are more. Left alone, it would have adapted to a machine no visitor owns.

Limited memory

We capped the memory available to the page at 512 MB

512 MB

A phone does not have unlimited memory. A page that only works because the test machine had plenty to spare is a page that will fail somewhere real.

Three runs of everything

Every measurement was taken three times, and we show all three

3 runs of each version

Measurements wobble. Taken once, a normal wobble looks like a result — which happened here: one run showed a version handling 7–11% more traffic, and the next showed the opposite. Three runs, with the spread shown, is what stops a wobble being reported as a finding.

How long people wait

Four different kinds of waiting, because "slow" is not one thing. A page can appear instantly and then refuse to respond, or respond instantly and show nothing for three seconds.

Largest Contentful Paint

How long until the biggest thing appears

The moment the largest image or block of text on the page finishes drawing. Not the first pixel — the one that makes the page look like the page.

Why it matters. It is the closest single number to "has this loaded yet" as a person experiences it. Everything before it, the visitor is looking at a mostly empty screen.

What good looks like Google calls under 2.5 seconds good. Over 4 seconds is poor.

How much to trust this Barely moved between runs. A difference bigger than the wobble is real.

First Contentful Paint

How long until anything appears

The first moment any content is drawn — a heading, a line of text, an image. It says the page has started, not that it is ready.

Why it matters. A blank screen feels broken. This is the point at which a visitor knows something is happening.

What good looks like Under 1.8 seconds is good.

How much to trust this Barely moved between runs. A difference bigger than the wobble is real.

Interaction to Next Paint

How long the page takes to react when you touch it

From tapping or clicking to the screen visibly responding. Measured across a real interaction rather than assumed.

Why it matters. It is the difference between a page that feels alive and one that feels stuck. A visitor forgives a slow load far more readily than a slow button.

What good looks like Under 200 milliseconds is good.

How much to trust this Most rows here held steady across runs. Home and Support centre and Product catalogue and Shopping basket did not — moved a lot between runs. Not reliable enough to compare — treat these as unknown.

Time to First Byte

How long the server took to start replying

From asking for the page to the first byte of the answer arriving.

Why it matters. Everything else waits behind it. A slow server pushes every other number out.

What good looks like Under 800 milliseconds. These measurements are on one machine with no network, so this is server thinking time only — a real connection would add to it.

How much to trust this Most rows here held steady across runs. Support centre and Contact form and Product catalogue and A product page and Shopping basket did not — moved a lot between runs. Not reliable enough to compare — treat these as unknown.

How annoying the page is

Two metrics for the things that make a page feel broken rather than slow.

Cumulative Layout Shift

How much the page jumps about while loading

A score, not a time. It adds up how far things move after they have already been drawn — the button that slides down as an image loads above it.

Why it matters. This is the metric behind tapping the wrong thing because the page moved underneath your finger. It is the most irritating failure on this list and the most avoidable.

What good looks like Under 0.1 is good. Zero is achievable and is what both stacks here manage on almost every page.

How much to trust this Identical every time. Any difference between the two versions is real.

Total Blocking Time

How long the page was too busy to respond

While JavaScript runs, the page cannot react to anything. This adds up the time spent in chunks long enough for a person to notice — over 50 milliseconds each.

Why it matters. It is a laboratory stand-in for responsiveness. High blocking time means taps land on a page that cannot answer yet.

What good looks like Under 300 milliseconds. Both stacks here are at zero, which is as good as it gets.

Total Blocking Timezero on every route, both stacks — the best available result, and nothing to plot.

How much to trust this Identical every time. Any difference between the two versions is real.

What the page costs to download

What has to come down the wire before any of the above can happen.

Page weight

How much has to be downloaded

Everything the page fetches — code, styles, photographs, video — compressed, as it travels.

Why it matters. On a slow or metered connection this is the whole experience. It is also the number most easily hidden by testing on a fast machine, where downloads are instant and weight appears free.

What good looks like No fixed threshold; it depends what the page is for. A page carrying photographs will always be heavier than one carrying text.

How much to trust this Identical every time. Any difference between the two versions is real.

How hard the device has to work

Downloading is half the cost. The other half is what the phone does with it once it arrives — which turns into battery, heat, and slowness on anything cheaper than a test machine.

Main-thread busy time

How much work the browser had to do

Total time the browser spent running code, calculating layout, and painting for one page load. The nearest thing to "how hard did this make the device work".

Why it matters. Work costs battery and heat, and on a cheaper phone it costs time too. Two pages can look identically fast on a good device and feel very different on a bad one.

What good looks like There is no official threshold. Lower is better, and the comparison between two stacks is the useful part.

How much to trust this Most rows here held steady across runs. Home and Support centre and Contact form and A product page and Shopping basket did not — moved a little between runs. Useful for direction; small differences are not meaningful.

JavaScript time

How long the browser spent running code

The part of the above that is specifically compiling and executing JavaScript.

Why it matters. It is the part most directly under a developer’s control, and the part a framework choice moves most.

What good looks like No official threshold. Compare the two columns.

How much to trust this Most rows here held steady across runs. Home and Shopping basket did not — moved a little between runs. Useful for direction; small differences are not meaningful.

Memory held

How much memory the page is using

What the page is still holding in memory once it has settled.

Why it matters. On a phone with several tabs open, a heavy page is the one the system throws away — so returning to it means loading it again.

What good looks like No official threshold. Lower is better.

How much to trust this Identical every time. Any difference between the two versions is real.

Are we comparing the same website?

Everything above is meaningless if the two versions do not produce the same page. This is the check.

Page structure

How many elements the page is built from

A count of the boxes, images, links and text blocks the page is made of.

Why it matters. Here it is a fairness check rather than a performance one. Both versions are meant to produce the identical page; if these counts differed, the comparison would be between two different websites and every other number would be meaningless.

What good looks like Identical between the two stacks. Anything else invalidates the report.

How much to trust this Identical every time. Any difference between the two versions is real.

What it costs the people building it

Everything above is about the visitor. This is about the engineers — how long they spend waiting for the computer instead of working. At eight teams and hundreds of developers, it is the largest single cost in the whole report.

First build

How long to build everything from scratch

From a clean checkout with nothing cached to a finished build of every application.

Why it matters. Every new developer waits through this once, and the continuous integration system waits through it on every change.

Rebuild after one change

How long to rebuild after editing one file

Change a single file, rebuild the application that owns it.

Why it matters. The number a developer meets most. Dozens of times a day, per person, across every team. At scale it is the largest single cost in this report.

Edit to seeing it

How long from changing code to seeing the change

A real edit, rebuilt, servers restarted, and the change confirmed present in a real browser.

Why it matters. The complete inner loop. Everything else about developer experience is downstream of it.

What this does not tell you

Worth saying plainly, because a report that only lists its strengths is an advertisement.

  • We ran everything 3 times. That is enough to spot an unreliable measurement and not enough to be precise about a small one.
  • Everything ran on one computer, not on a range of real devices. Download sizes would be identical anywhere; timings would not.
  • There is no real network — we simulated a slow connection rather than using one, so the numbers are repeatable but idealised.
  • The Svelte version copies the React one exactly, down to the page structure, because that is what makes the comparison fair. A team building it from scratch in Svelte might do some things differently.
  • Both versions use the same build tool. This compares two frameworks, not two build tools.

Every number here comes from the same dataset as the technical report, which carries the full method, all raw measurements, and the exact conditions each was taken under.
